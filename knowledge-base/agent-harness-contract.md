# Agent and harness contract

Status: **confirmed implementation handoff**. The user confirmed shared understanding after the agent/harness design interview. Agreed behavior is separated from external data-policy dependencies and operating values that require measurement. This document is not a list of allowed natural-language questions. The trader-vocabulary research supplied the accepted first capability set below.

## Purpose and scope

The agent answers flexible analytical questions from market observations retained by the product. It may combine supported calculations rather than match a question to a fixed tool. The first required end-to-end example is the gain-plus-volume-frequency question in [agent-design.md](agent-design.md). News, causal explanations, forecasts, and actions that change market data are outside the first agent's scope.

The agent and explorer share one analytical service and metric definitions. The model interprets a question and proposes a versioned **Analytical Request**. Trusted application code validates its structure and meaning, compiles the calculation, and returns a structured result. The model has no SQL or database credentials. It cannot authorize an action by writing persuasive text in a request or a tool response.

## Turn flow

1. Accept a question in a selected Agent Conversation and record a new Agent Turn. A new conversation has no context from another conversation.
2. Supply the agent with the current question, relevant context from that conversation, the supported analytical vocabulary, and the available read-only tool contract.
3. Interpret the question. Use a defensible documented convention when possible and record the assumption. Ask for clarification only when no defensible interpretation exists.
4. Propose an Analytical Request. Validate its schema, supported operations, units, dates, universe, grouping, result size, and compatibility. A rejected request is never executed. The harness may allow a bounded repair attempt; the exact budget remains open.
5. Execute the accepted request through the read-only analytical service. Prefer one set-based calculation when it suffices. Additional calls require a concrete reason, such as checking coverage or a result that needs inspection, and remain inside the turn budget.
6. Return one of: an evidence-backed answer, a clarification question, an explicit unsupported-capability explanation, or a calculation/error result. Never fill a missing result with a plausible number.
7. Persist the turn's question, validated request, evidence reference, answer or failure, and operational trace. Retain the full visible conversation until explicit deletion. For model input, use recent turns and a concise summary of older turns, with access to original turns when needed; do not mix conversations.

Each agent turn is a **Temporal workflow** that continues after the browser disconnects; reopening the conversation shows its current state or completed answer. The workflow coordinates a bounded interpretation → validation → analytical tool → answer loop. Model calls, database reads, and other external I/O run in activities, not workflow code, so replay remains deterministic. The application persists the conversation and answer; Temporal records execution state and retries. The explorer remains a direct API/query path. The workflow must avoid storing full market-data result sets or secrets in its history; use references and bounded summaries. The exact workflow/activity decomposition and framework integration remain engineering choices.

A conversation is **linear**: the app does not accept another user message into it until its active turn finishes with an answer, clarification request, unsupported result, or error. The next message can then use the preceding turns as context. Distinct conversations can run concurrently and never share context.

The active-turn UI offers **Cancel**. Cancelling requests Temporal workflow cancellation, marks the turn cancelled, and reopens input after cancellation reaches a terminal state. Any already completed read-only calculation remains harmless; a cancelled turn does not publish a fabricated answer. Deleting a conversation with an active turn also cancels its workflow before removing conversation-owned records.

## Analytical Request v1 shape

The request names a supported universe, date window, source/feed and price-basis policy, measures, conditions, aggregation or grouping, ordering, and output limit. A metric definition states its input grain, units, missing-data rule, and compatible operators. The first vocabulary combines daily open/high/low/close/volume fields with period returns, comparisons, counts, percentages, averages, sector grouping, and rankings. The service resolves the latest published catalog snapshot and trading sessions, pins them for the calculation, and returns the resolved values with the result.

The request must not contain SQL fragments, arbitrary table or column names, joins, functions, or free-form code. Predicates use enumerated fields and operators with typed values. The first-release vocabulary below is accepted at the capability level; exact metric definitions still need versioning and provider verification. It must cover the required gain-plus-volume-frequency question without a special case for that sentence. Later capabilities such as correlation and longest sector leadership need their own defined semantics before they can be added.

The accepted **v1 capability set** is stock ID, date-valid ticker, current sector, session date, OHLCV; period percentage return; expected and observed session counts; count/fraction of sessions matching a typed daily condition; eligible/positive stock counts; Sector Breadth, Sector Return, Market Return, and Stock Excess Return. Typed comparisons are `=`, `<`, `<=`, `>`, `>=`, and bounded membership for compatible fields; conditions can be combined with `and`, then grouped, sorted, and limited. “Gained most” ranks stock period return, while the explorer's stock leaderboard ranks excess return. Stable ordering resolves ties without changing the reported tied value. Indicators, correlations, forecasts, and causal explanations are later capabilities. Precise rules for basis, bar status, listing history, and provider feed still govern whether a particular measure can be used.

Daily conditions have two distinct forms. An **absolute count** such as “up on at least 100 days” requires at least 100 observed, calculable days satisfying the condition; a stock with only 50 observed days cannot qualify. A **relative frequency** such as “up on at least 50% of trading days in the range” divides qualifying days by the days with a usable observation for that stock in the requested range. A newly listed stock or one with fewer provider bars can qualify based on its observed days. Missing days are neither qualifying nor failing days in that percentage. Show both the numerator and observed-day denominator, plus observed-day coverage of the requested range and known listing period, so the user can see the smaller sample. There is no fixed minimum observed-day count in the first version: even 1/1 can qualify, visibly labeled as a one-day sample. Revisit a minimum only if actual usage shows the need.

A stock request using only daily-frequency measures is eligible when it has at least one usable daily observation in the window; a missing comparison or final return close does not exclude it. If the request also selects a return-based measure, return eligibility applies and both closes are required. The tool reports which rule was used through its metric version, eligible count, exclusions, and nullable return fields.

## Answer and evidence contract

An answer identifies the calculation, resolved date window, eligible and requested stock counts, eligible percentage, source/feed, data as-of time, and assumptions that affect the result. A result using incomplete data may say, for example, “among X% of stocks scanned.” It cannot claim a winner across the complete requested universe when excluded stocks could change it. Relevant details live in an expandable evidence section; a large aggregate does not need arbitrary sample rows.

The tool result should carry machine-readable values for the metric and request versions, pinned catalog snapshot and sector as-of time, source/feed/price basis, resolved sessions, calculated values, eligibility and exclusion counts, and calculation time. The agent explains these returned facts; it does not recalculate authoritative numbers in prose. If a later observation correction changes an answer, new calculations use the current accepted observation. Exact replay of old answers is deferred.

The final response should separate **trusted result fields** from **agent-written explanation**. The application renders the primary result, numbers, dates, coverage, and source from the analytical service's structured output. The agent supplies a concise interpretation and assumptions tied to that result ID. This reduces reliance on text grading for the facts users depend on, while preserving flexible prose and follow-up conversation.

## Enforced boundaries

- Only approved read-only analytical tools are exposed to the model. Trusted code validates every request and uses a read-only database role, parameterized queries, and bounded execution.
- User text, prior conversation text, stored names, and tool output are untrusted input. Instructions inside them cannot expand tool permissions or bypass validation.
- Bound tool calls, query time, date span, returned rows, and model turns. The first numeric limits should be measured against the homelab and then configured, rather than assumed here. At the budget limit, return a verified and clearly scoped partial result if one exists; otherwise explain the limit and offer to narrow or retry the question.
- A timeout, rejected request, unavailable metric, missing source, or failed query yields a specific limitation or retryable error. The agent must not report an unverified calculation as fact.
- The manual release override bypasses only the test gate. It does not change runtime read-only permissions or request validation.

## Implementation handoff: workflow and tools

Use one workflow ID derived from the Agent Turn ID. The API atomically creates the turn only if its conversation has no active turn; a repeated submission with the same request ID returns the existing turn. A different submission while that conversation has an active turn is rejected as busy. Distinct conversations can run at the same time. The API exposes turn status and the completed answer so a browser can reconnect without restarting work.

The turn moves through `running` and one terminal state: `completed`, `needs_clarification`, `unsupported`, `failed`, or `cancelled`. `cancel_requested` is an intermediate state. The input stays disabled until the turn reaches a terminal state. A clarification request ends that turn; the user's clarification starts the next turn in the same conversation. Cancellation is explicit; browser disconnection is not cancellation. Persisting a terminal result must be idempotent by turn ID so a retried activity cannot duplicate an answer.

Temporal coordinates bounded steps. Activities load conversation context, call the model, validate/execute an Analytical Request, persist turn output, and create or refresh an older-turn summary when needed. The workflow keeps small IDs, state, counters, and bounded result references rather than entire market-data pages. Completed activity results are replayed by Temporal; external model and database calls are not made from workflow code. Read/query and model-call failures may retry within configured limits. A semantic validation rejection is returned to the agent for at most a bounded repair attempt; it is not retried as an infrastructure failure. Permanent unsupported requests finish as `unsupported`. A failed dependency or exhausted budget finishes with a specific limitation and any verified scoped partial result. The activity implementation and framework can be chosen during coding without changing these product behaviors.

The analytical tool accepts only a versioned typed request built from registry IDs and typed values. Its contract includes: universe and resolved window; requested row grain; selected measure IDs; optional typed daily condition and count/fraction reduction; compatible stock/group predicates; group-by, sort, and bounded limit. It validates units and grain before compiling parameterized, set-based queries. It returns a structured result envelope with resolved policy versions, rows or aggregates, eligibility and observation counts, exclusion reasons, source/as-of values, and evidence references. An empty but valid result differs from tool failure. All requests, validation rejections, tool results, and model decisions are traceable by turn ID without storing secrets or full raw provider responses.

At sector grain, only `sector_code` predicates are valid. Ticker and stock ID predicates require stock grain; applying them only to the sector row selection would misrepresent a whole-sector breadth or return as a filtered calculation.

For the required volume-and-gain case, the request selects the current catalog and previous completed calendar month, counts observed usable days with `daily_dollar_volume > USD 100000`, filters stocks where `qualifying_days / observed_usable_days >= 0.80`, ranks by period return descending, and limits to the leading result. Both `qualifying_days` and `observed_usable_days` must be returned. For daily dollar volume use provider-reported traded notional when available; otherwise estimate share volume × daily VWAP, falling back to share volume × daily close if VWAP is unavailable. The tool result and answer must identify an estimated value, its price input, and formula. [GitHub issue #4](https://github.com/maorts14/market-eagle/issues/4) tracks later review of this working rule. The comparison close before the first included session is required for period return. The same measure definitions are used by the explorer. This is a composition of operations, not a special tool for that wording.

Store the full original turns until conversation deletion. A model-context summary is a cache derived from a known span of turn IDs, not the source of truth. Store its source span and version; use recent original turns plus that summary within the context budget and fetch older original turns when a follow-up depends on them. A summary cannot grant tool permissions or substitute for validating the current request. Exact summary length and operating token budget are configurable engineering values.

## Evaluation and release

The test suite covers interpretation and tool-choice decisions, request validation and query correctness, and complete question-to-answer runs. Include ordinary and structurally different phrasings, follow-up questions, incomplete observations, unsupported causal questions, injection attempts, and the required gain-plus-volume-frequency example. Use a substantial synthetic market history for calculation tests, such as five stocks over two years, rather than relying only on a few trading days. Check the validated plan and numeric result before grading answer wording. Failures should identify whether the fault arose in interpretation, validation, data, calculation, or presentation.

Daily-frequency fixtures must distinguish counts from percentages: a stock with 50 observed days cannot satisfy “at least 100 qualifying days,” while 30 qualifying days out of 50 observed days satisfies “at least 50%,” with the 30/50 sample and requested-range coverage shown. Include newly listed stocks and missing provider bars separately so the reported context is accurate.

Passing the suite gates release. Wrong calculation results or a broken runtime permission/validation boundary are critical failures that fail the gate. An operator can explicitly release despite a failed or incomplete gate; record who overrode it, why, the test run/version, and the failed checks. The exact passing threshold for non-critical answer-quality cases remains open.

The implementation gate contains a fixed **core suite** whose required factual, coverage, conversation-isolation, and runtime-boundary criteria must all pass. A separate, growing evaluation set measures broader phrasings and clarity; its numeric release threshold is chosen after a human-labeled baseline exists, rather than invented before representative outputs are available. The operator override is a deployment action, not an agent tool or an app-visitor action. Its durable record includes the operator identifier, reason, timestamp, model and metric versions, evaluation run ID, and failed or unrun checks. It does not disable runtime guards.

Answer quality should be measured against **observable criteria**, not whether the prose matches one reference sentence:

1. **Grounding:** every factual number, ranking, source, and date in the answer agrees with the structured tool result; no unsupported causal claim or invented fact appears. Critical factual errors fail the case.
2. **Completeness:** the answer addresses the user's actual question and includes material assumptions, coverage, and limitations. A response can use different wording and still pass.
3. **Clarity:** a reader can identify the result first, understand the calculation and caveats, and inspect relevant evidence without unnecessary raw rows.
4. **Conversation use:** follow-ups resolve references from the correct conversation and do not import context from another conversation.

For each scenario, keep a test question, fixture data/tool result, expected factual claims, forbidden claims, and a small criterion-by-criterion rubric. Check objective fields and numbers programmatically. Human reviewers label a representative set of responses against the rubric and record why they pass or fail. An automated model judge may help run more cases, but compare its verdicts against those human labels and review disagreements; it is not the sole authority for the release gate. Capture the Temporal/tool trace so an error can be attributed to planning, validation, calculation, or presentation.

Free-text grading has three complementary layers. **Code** verifies the chosen Analytical Request, tool result, rendered result fields, and required evidence against a test fixture. **A separate evaluator model**, given the question, authoritative tool result, final prose, and a narrow rubric, labels semantic claims that cannot be checked by string matching: whether the answer actually addresses the question, whether its scope is accurate, and whether it invents unsupported claims. The evaluator must return per-criterion pass/fail, a short reason, and the answer text supporting that verdict. **Human review** labels a smaller reference set, checks evaluator agreement, and resolves uncertain or disputed failures. The same test should include multiple valid phrasings and deliberately wrong answers so the evaluator cannot pass every fluent response. The evaluator's verdict is evidence for the gate, not proof by itself.

Build the first evaluation dataset **before launch** from small synthetic market fixtures, documented product rules, and representative questions. After real use begins, review questions, traces, failures, and user feedback to add new cases that the initial set missed; do not assume the original suite covers all future wording. A new real-use case needs an expected behavior or human label before it becomes a gate. Separate release-blocking cases from exploratory monitoring cases, version the dataset/rubric, and keep the gate independent of any particular vendor evaluation platform.

For example, a response can say “ABC led among 482 of 500 stocks with enough data” in different words. The test checks that the stock, return, 482/500 coverage, date range, and source match the tool result; that it does not claim ABC led all 500; and that the answer is understandable. A response with beautiful wording but a wrong stock or invented explanation fails. OpenAI's [agent-evaluation guidance](https://developers.openai.com/api/docs/guides/agent-evals) recommends traces for debugging agent decisions and repeatable datasets for regressions; its [dataset guidance](https://developers.openai.com/api/docs/guides/evaluation-getting-started) describes human annotations and graders. This project can implement the rubric independently of any particular evaluation platform.

## Calibration and external dependencies

1. Version the precise metric definitions and accepted provider/feed/basis/bar-status choices after data-source verification. A minimum observed-day count is deferred until actual usage warrants it.
2. Select configured numeric limits for model calls, analytical calls, query time, total turn time, date span, result rows, and context size from homelab measurements. The harness must enforce limits from its first implementation even if these values change.
3. Build and human-label the initial evaluation cases, verify evaluator agreement on deliberate good and bad answers, and set the broader quality threshold from that baseline before release.

Price basis, provisional-day storage/selection, and provider freshness are shared data policies tracked in [decision-tree.md](decision-tree.md). The settled inclusion rule uses an available provisional bar when the requested range contains today; the harness should not invent agent-only meanings.
